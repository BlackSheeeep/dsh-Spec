# 报告方法论

报告写给需要做决定的人，不是写给整理归档文件的人。任何一份报告都必须先说明这项工作站在哪条主线上、让什么能力前进或恢复到什么程度，再说明具体改了什么；禁止从文件、任务或提交顺序讲起。下面的规则是硬约束，不是写作建议。

## 主线锚定三步

先定位，再展开，最后回到主线。三步缺一不可，顺序不能倒。

### 一、定位：这项工作站在哪条主线上

写正文之前，先用一句话回答四个问题：

- **大系统**：这个仓库 / 产品最终交付什么，为谁解决什么问题？
- **核心主线**：当前阶段最关键的一条推进线索是什么？
- **支线能力**：本次工作服务于哪条支线、哪个能力（capability）？
- **最终目标**：这项工作最终让主线的哪个目标更接近达成？

主线来源只有两种，必须在报告头部标注：

- **项目主线卡**：`openspec/report-context.md` 存在时优先使用，标注「主线来源：项目主线卡」。
- **推断**：主线卡缺失时，从 `openspec/config.yaml` 的 context、主 specs 的 capability Purpose、proposal 的 Capabilities / Impact、design 的 Context 归纳，标注「主线来源：推断」，并列出缺失的主线信息与推断依据。

不得虚构系统目标、组织背景或业务指标。定位结论要写进报告首屏的「一页速览」与「主线定位」，不能只留在分析过程里。

### 二、展开：实现了什么功能、修复了什么问题

按「问题 / 目的 → 改动 → 之前怎样 / 之后怎样」展开：

- **问题或目的**：这次工作要解决的真实问题、要达到的目的，用主线语言描述，不要只抄 proposal 标题。
- **改了什么**：实现了什么功能、修复了什么缺陷、调整了什么约束；按能力 / 支线归组，不按文件或任务编号罗列。
- **之前怎样 / 之后怎样**：给出可对比的行为差异，并逐条标注证据等级（见「证据分级」）。旧文本未留存时明写，不得脑补。

展开层只保留支撑判断的关键信息；工件清单、逐任务勾选、文件落点与完整验证读数一律下沉到折叠层。

### 三、回归主线：成果必须用主线语言表述

结论回到第一步定位的主线：

- **用主线语言写结果**：例如「让主线 X 的 Y 能力恢复达标」「使 Z 链路具备 A 能力，支撑下一阶段目标」，而不是「修复了 N 个 bug」「完成了 change xxx」。
- **写影响面**：哪个能力 / 哪类用户 / 哪条链路受影响，哪些明确不受影响。
- **写边界与未闭合项**：本次没有覆盖什么、哪些结论仍待验证、哪些依赖后续工作。

禁止以 change 名或「修复了 bug」「实现了一个功能」作为标题或结论。标题必须让人一眼看出主线位置与价值。

## 渐进披露

按 30 秒层 → 5 分钟层 → 深入层组织，先结论后细节：

- **30 秒层**（`00 一页速览`）：一句话主线定位 + 一句话成果。读者只读这一段也能复述这项工作对主线的意义。
- **5 分钟层**（`01`–`04` 节）：主线定位链、本次工作、前后差异、回归主线。回答「为什么做、做了什么、变成什么样、对主线意味着什么」。
- **深入层**（`06 细节与证据`）：工件清单、任务完成度、文件落点、验证读数、原始证据路径。

细节默认折叠可展开：所有深入层内容放进默认收起的 `<details>`，需要时再展开；首屏不得出现任务清单、长篇文件列表或成段代码。方法论与概念（验证方式、可复用经验、术语表）单独成节（`05 方法论与概念`），不要混入主线叙事。

## 时间段汇总报告

时间段报告回答「这一段时间整体推进了主线上的什么」，不是若干单变更报告的合集。

- **范围口径**：按归档日期区间（归档目录名 `YYYY-MM-DD-<change>` 的日期前缀）统计，包含起始与结束日期；报告标题与「归档信息」同时展示区间，不使用单个 change 名。
- **先统一，再分述**：开头先给该时间段在核心主线上的统一定位与整体成果（主线发生了什么变化），再按支线 / 能力归组展开。
- **按支线 / 能力归组**：组内按时间线排列 change；同一能力被多个 change 修改时按时间线归并，不按归档顺序平铺。
- **变更清单**：必须有「本期变更清单」表格，列出每个纳入 change 的归档日期、change 名、所属支线 / 能力、一句话结果（主线语言）。
- **逐 change 折叠**：每个 change 在细节节占一个默认收起的折叠块，只放事实卡级摘要与证据；不要复制单变更报告全文，更不要把 N 份报告拼接成一份。
- **降级标注**：子 agent 不可用或改为顺序执行时，在「方法论与概念」或「归档信息」中如实标注执行方式。
- **可追溯**：报告保留纳入的 change 归档路径清单与生成时间，可据此复核。

## 子 agent 编排

时间段报告默认并行取证，降低时延，同时用固定字段保证各 change 口径一致。

- **一 change 一 agent**：每个纳入的 change 分派一个只读子 agent，只读取归档工件与主规格，不写文件、不修改 proposal / design / tasks / delta / 主规格。
- **事实卡固定字段**：每个子 agent 必须返回一张事实卡，字段固定、不得增删：
  - `change`：change 名
  - `归档路径`：归档目录
  - `日期`：归档日期
  - `capabilities`：涉及的 capability / 支线
  - `问题`：要解决的真实问题
  - `目的`：预期目的
  - `改动`：实现了什么 / 修复了什么
  - `before-after`：之前 → 之后，并附证据等级（原文 / 推断 / 未验证）
  - `验证证据`：测试、运行读数，或「归档材料中未见」
  - `边界`：未覆盖、未验证、依赖项
  - `主线候选`：该 change 在主线上的位置候选，供主会话归组
- **并发建议 4–6**：超过 6 个 change 时分批派发，单批不超过 6 个，批间先汇总再继续。
- **顺序降级**：当前会话不可用子 agent、或 change 数量过多时，改为顺序只读调查；报告必须标注降级（例如「本次为顺序取证，未使用并行子 agent」）。
- **主会话只做汇总**：拿到全部事实卡后，由主会话负责跨 change 归组、主线综合与唯一一份报告的撰写；不得让子 agent 各写一段直接拼接。
- **显式处理冲突**：同一能力被多个 change 修改时按时间线归并；无法归并的分歧写成「口径冲突 / 未闭合」，不得取其一冒充全部。
- **不阻塞**：子 agent 失败或事实卡不完整时，主会话补读关键工件，报告标注缺失来源，不因此放弃整份报告。

## 反模式

- 用 change 名、「修复了 bug」「实现了一个功能」当报告标题或结论。
- 把任务清单勾选（4/4、全部完成）当作成果；任务完成度是过程证据，不是主线价值。
- 细节铺满首屏：打开报告先看到文件清单、代码 diff、命令输出，读者找不到主线。
- 术语不解释：delta、capability、schema 等内部词直接堆进正文，不给术语表。
- 编造数字或证据：没有测试读数却写「全部通过」，没有指标却写「提升 30%」。
- 把推断写成确定事实，或把「未验证」说成「已达标」。
- 时间段报告把多份单变更报告拼接：每段都以 change 名开头，读完仍不知道这一段时间推进了什么。
- 按文件、任务编号或提交顺序组织报告，而不是按主线 / 能力组织。
- 只写「做了什么」，不写「之前怎样 / 之后怎样」，读者无法判断变化。
- 同一份报告里出现两套主线定义，或每条支线各配一条互不相干的主线。

## 证据分级

每条结论都必须能对应到一个证据等级，不允许无标签的断言：

- **原文**：归档工件（proposal / design / delta）中的逐字文本，或工作区 git 历史中可定位的主规格旧版本；引用时给出文件与位置。
- **推断**：基于归档材料合理推导，但没有逐字旧文本支撑；必须写明「推断」及推理依据。
- **未验证**：有改动但缺少测试 / 运行读数 / 真机证据；不得写成已验证。
- **归档材料中未见**：归档目录没有该信息（例如无测试记录、无指标）；明写「归档材料中未见」，不要沉默，也不要补编。

强约束：

- **delta 是 after 的权威**：新行为以归档 delta spec 为准，不凭记忆或旧文档描述之后状态。
- **旧文本未留存**：`MODIFIED` / `REMOVED` 需求在归档时只保留 after 文本，旧文本不随归档保存；没有 git 历史或其他原文时，前置行为只能标「推断」，并注明「旧文本未留存」。
- **不编造**：不得虚构旧行为、测试结果、性能数字、用户反馈或上线效果；缺证据时降低断言强度或明写缺失。
- **时间段报告逐 change 保留等级**：不得把多个推断合并成一个看似确定的事实；汇总结论要能追到具体 change 与证据等级。

## 命名与归档口径

- **单变更报告**：`<报告根目录>/<change-name>/index.html`；选择写入归档目录时为 `openspec/changes/archive/<归档目录>/report.html`。
- **时间段报告**：`<报告根目录>/<from>_<to>/index.html`，目录名即范围，如 `2026-10-01_2026-10-22`。
- **引用保留**：报告正文「归档信息」与页脚保留 change 名或时间段、归档路径、主规格路径、生成时间；写到归档目录之外时，归档目录的 `report.json` 记录报告路径、生成时间、模板版本与 change 名；时间段报告在同目录 `report.json` 记录范围、生成时间、模板版本与纳入的 change 清单（含各自归档路径）。
- **口径声明**：报告是给人读的说明，**不替代规格真相源**；行为契约以 `openspec/specs/` 主规格为准，验收读数以原始证据文件为准。不得在报告里另立一套规格。
- **只写报告**：报告生成只写报告文件与必要的 `report.json` 指针，不修改归档工件与主规格。
